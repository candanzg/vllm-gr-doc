# vllm-gr 离线 Beam 端到端时延（H20-3e，main `bf9db2a`）

本目录记录 vllm-gr 在 H20-3e 单卡上的离线 Beam Search 端到端时延，覆盖 168 个用例，每个用例报告 mean、p50、p90、p99。当前只含 U 模式（不启用受限表）；C 模式（启用受限表）仍在测量，完成后补入。

## 结论

1. **168 个用例全部完成，无失败。** 输入长度 7 档（256 ~ 10240）× Beam 宽度 6 档（32 ~ 1024）× batch 4 档（1/2/4/8）。
2. **尾部很平。** p99 / p50 的中位数为 1.013，最大为 1.089（W=256、L=512、B=1：p50 38.72 ms，p99 42.17 ms）。
3. **p99 的样本量偏小。** 每个用例只有 48 个样本，p99 约等于最大值，一次抖动就会拉高，p99 之间 1–2% 的差别不应当作真实差异。
4. **与 2026-10-31 的旧矩阵（`33a1fdb`，同口径 U 模式）逐点对比：宽 Beam 变快，窄 Beam 持平。** 168 个点都有对应，没有任何一点慢超过 2%，114 个点更快。按 Beam 宽度看新/旧时延比的中位数：

   | W | 32 | 64 | 128 | 256 | 512 | 1024 |
   |---|---:|---:|---:|---:|---:|---:|
   | 新 / 旧 | 1.006 | 1.003 | 0.999 | 0.957 | 0.935 | 0.901 |

   最大的改善在 W=1024、L=256、B=8，新版是旧版的 0.849 倍。这个对比只说明两个版本的差别，没有拆分是 vllm-gr 本身的改动、vLLM 升级到 0.30.0，还是测试套件改动带来的。

## 口径

| 项目 | 内容 |
|---|---|
| 端到端时延 | 一次 `generate()` 调用处理 B 个请求的墙钟时间，从提交到 token 与分数全部取回，不除以 B |
| 样本 | 每个用例 48 个：3 轮 × 每轮 16 批；预热批次不计入 |
| 分位数 | 线性插值（与 numpy 默认一致）。48 个样本时 p99 落在最大与次大样本之间 |
| 硬件 | NVIDIA H20-3e，单卡，TP=1，BF16 |
| 模型 | OneRec-1.7B |
| 代码 | vllm-gr main `bf9db2a`，vLLM 0.30.0，`gpu_memory_utilization=0.6` |
| 测试套件 | `competitor-suite` 上游 `35135a1` + 一处适配：Beam 宽度可到 1024，每个父节点的候选数 K = min(W, 256) |
| 输出策略 | `eos_policy=fixed3`，固定生成 3 个 token |

K 固定上限 256，Beam 宽度增大不会增大 K。这与 2026-10-31 的旧矩阵口径一致。

## 测量过程中的一次崩溃与处理

第一次运行把 7 档长度放在同一个引擎里，所有 6 个 Beam 宽度都在从 L=4096 切到 L=8192 时报 CUDA 错误（`unspecified launch failure`），引擎退出。处理方式是把 L=8192 和 L=10240 放到独立作业中重新测，用全新的引擎。重新测的 48 个点全部完成。

崩溃的真实原因尚未查明：未做 `CUDA_LAUNCH_BLOCKING=1` 的复现，也没有证据说明它与「Decode 重捕获时回收了仍被 Prefill 图引用的内存」是同一个问题。因此，数据可用，但在该形状上遇到的崩溃没有被修复，只是被绕开。

## 校验

- 168 个用例的 mean 与套件自己报告的 `batch_mean_ms` 逐一核对，最大偏差 0.005 ms。
- 每个用例满足 p50 ≤ p90 ≤ p99。
